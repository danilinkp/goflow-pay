# Нагрузочное тестирование балансировки nginx

Инструмент: [k6](https://k6.io) 0.52.0 в контейнере `grafana/k6:0.52.0`.

Основной отчёт — дашборд Grafana «GoFlow Pay — нагрузочное тестирование» (`/monitoring/d/goflow-loadtest`): таблица прогонов, выводы и методика; клик по прогону открывает его итоги и графики со стороны k6 и сервера. k6 отправляет метрики в Prometheus, каждый прогон получает `testid`. Ниже — то же самое в виде текста по первым прогонам 10.11.2026; прогоны 11.11.2026 (после перевода логов сервисов в JSON) лежат в `results/2026111*` и разобраны на дашборде.

## 1. Что проверяем

- **Чтения.** GET-запросы к `/api/v1` и `/api/v2` делятся между тремя экземплярами gateway в соотношении 2:1:1. Основной экземпляр `gateway` работает с правами на запись, `gateway-ro-1` и `gateway-ro-2` подключены к БД пользователем `readonly`.
- **Записи.** Все POST-запросы попадают только на основной `gateway`.
- **Задержка и ошибки.** Балансировка не добавляет заметной задержки и ошибок при нормальной нагрузке.
- **Предел стенда.** Найти, где он находится, и понять, во что он упирается.
- **Лимит запросов.** Убедиться, что `limit_req` продолжает защищать API от флуда с одного адреса.

## 2. Ожидаемое поведение и целевые показатели

Сформулированы до запуска и записаны в `thresholds` сценария `k6/balance.js`. Если хоть один не выполнен, k6 завершается с ненулевым кодом.

| Сценарий | Показатель | Цель |
|---|---|---|
| steady, mixed | доля ошибок `http_req_failed` | < 1% |
| steady, mixed | p95 чтения | < 300 мс |
| mixed | p95 записи | < 500 мс |
| steady, mixed, ramp | доля чтений на основной `gateway` | 48–52% (2 из 4) |
| steady, mixed | ответы от неизвестного экземпляра | 0 |
| mixed | доля записей на основной `gateway` | 100% |
| ratelimit | доля ответов 429 при 50 rps с одного IP | > 50% |

**Гипотезы:**
- Весовой round-robin даёт доли 50/25/25 с точностью до единиц запросов независимо от нагрузки, потому что nginx выбирает экземпляр по весам, а не по времени ответа.
- Расход CPU экземплярами будет в той же пропорции 2:1:1.
- Предел стенда определит ноутбук, на котором крутятся все 45+ контейнеров, а не nginx.

## 3. Стенд и конфигурация

**Хост:**
- 8 логических CPU, 7,5 ГБ RAM, 12 ГБ swap;
- Arch Linux, Docker 29.8.1;
- все контейнеры (стенд, зеркало, мониторинг, k6) работают на одной машине.

**Экземпляры:**
- основной стек: `gateway`, `auth`, `accounts`, `transactions`;
- копии только для чтения: `*-ro-1` и `*-ro-2` (`READ_ONLY=true`, пользователь БД `readonly`, Postgres тот же);
- стек зеркала `/mirror` в тест не входит.

**nginx** (`nginx/conf.d/default.conf`):

```nginx
map $request_method $api_upstream {
    GET     api_read;
    HEAD    api_read;
    default api_write;
}

upstream api_read {
    zone api_read 64k;
    server gateway:8080 weight=2 resolve;
    server gateway-ro-1:8080 weight=1 resolve;
    server gateway-ro-2:8080 weight=1 resolve;
}

upstream api_write {
    zone api_write 64k;
    server gateway:8080 resolve;
}

location /api/ {
    limit_req zone=api burst=20 nodelay;
    add_header X-Upstream $upstream_addr always;
    proxy_pass http://$api_upstream;
}
```

**Лимит запросов и генератор нагрузки.**
- `limit_req` пропускает 10 запросов/с с одного IP. k6 работает с одного адреса, так что упёрся бы в эти 10 rps, и тест проверял бы лимит, а не балансировку.
- Поэтому k6 запускается в отдельной docker-сети `goflow_loadtest` (172.29.250.0/24). Для неё ключ лимита пустой (`geo` + `map`), а пустой ключ nginx не ограничивает.
- Для всех остальных клиентов лимит действует. Это проверяет отдельный сценарий `ratelimit`, запускаемый из обычной сети стенда.

## 4. Сценарии и объём нагрузки

**Подготовка (`setup`).** Перед каждым прогоном k6 регистрирует 5 компаний и создаёт по 2 счёта. Эти записи проходят через nginx и тоже учитываются.

**Чтения.** Каждая итерация — случайный из пяти GET-запросов от имени случайной компании:
- `GET /api/v1/companies/accounts`
- `GET /api/v1/accounts/:id/balance`
- `GET /api/v2/accounts`
- `GET /api/v2/accounts/:id`
- `GET /api/v2/auth/me`

**Записи (mixed).** `POST /api/v1/accounts`.

Нагрузка задаётся частотой запросов (open model, `*-arrival-rate`), а не числом пользователей. Поэтому задержка ответа не снижает подаваемую нагрузку.

| Сценарий | Executor | Нагрузка | Длительность | Запросов |
|---|---|---|---|---|
| steady | constant-arrival-rate | 150 GET/с | 2 мин | 18 000 |
| mixed | constant-arrival-rate ×2 | 150 GET/с + 15 POST/с | 2 мин | 18 000 + 1 800 |
| ramp | ramping-arrival-rate | 50 → `RAMP_PEAK` GET/с, ступени по 30 с с удержанием | 4 мин | 270–480 тыс. |
| ratelimit | constant-arrival-rate | 50 GET/с с одного IP, без исключения из лимита | 20 с | 1 000 |

## 5. Как измерялось распределение

Используются три независимых источника.

1. **k6.** Каждый ответ API несёт заголовок `X-Upstream` с адресом выбранного экземпляра. `run.sh` перед стартом узнаёт IP контейнеров через `docker inspect` и передаёт их в k6. Скрипт относит каждый ответ к экземпляру: счётчики `reads_gateway*`, доли `read_on_primary` и `write_on_primary`.
2. **Access log nginx.** Формат `upstream` пишет метод и `$upstream_addr`. После теста `run.sh` разбирает лог за время прогона (`nginx-split.txt`).
3. **CPU экземпляров.** До и после теста `run.sh` читает `usage_usec` из cgroup каждого контейнера (`cpu.txt`). Это проверяет, что распределяется реальная работа, а не только запросы.

Ещё p95 по 30-секундным окнам считается из сырого CSV k6 скриптом `stages.py` (`stages.txt`).

## 7. Почему балансировка работает именно так

1. **Алгоритм.** nginx по умолчанию использует *smooth weighted round-robin*.
   - У каждого сервера есть текущий вес. На каждом запросе ко всем текущим весам прибавляется их базовый вес. Выбирается сервер с наибольшим текущим весом, и у него вычитается сумма всех весов (4).
   - Для весов 2/1/1 это даёт повторяющийся цикл из четырёх запросов: `gateway`, `ro-1`, `ro-2`, `gateway`. Проверка: `curl` 8 раз подряд вернул `gateway gateway ro-1 ro-2 gateway gateway ro-1 ro-2` (тот же цикл со сдвигом).
   - Поэтому при 18 000 запросах доли получаются точными, а не «примерно 50/25/25».
2. **Общий счётчик для всех worker'ов.** У `api_read` есть `zone`, то есть состояние балансировщика лежит в общей памяти всех worker-процессов nginx. Без `zone` у каждого worker'а был бы свой цикл, и общая доля была бы лишь приблизительной.
3. **Время ответа не учитывается.** Round-robin не смотрит ни на задержку, ни на загрузку экземпляров. Под перегрузкой (6.3, прогон 2) пропорция осталась 2:1:1, хотя основной экземпляр был нагружен вдвое сильнее. Алгоритм `least_conn` распределял бы по числу активных соединений, и доли под перегрузкой сместились бы к менее занятым копиям.
4. **Разделение чтения и записи.** Его делает не upstream, а `map $request_method $api_upstream`. GET и HEAD идут в `api_read`, остальные методы — в `api_write`, где есть только `gateway`. Поэтому 100% записей на основном экземпляре — свойство конфигурации, а не статистики.

## 8. Выводы

1. **Все целевые показатели выполнены:**
   - 0 ошибок во всех сценариях, кроме намеренных 429 в `ratelimit`;
   - p95 ниже целей на два порядка;
   - доля основного экземпляра 50,00%;
   - 100% записей на экземпляре с правами на запись.
2. **Балансировка доказана тремя независимыми источниками:** заголовок `X-Upstream` в k6, access log nginx и расход CPU по cgroup. Все три дают 2:1:1, CPU даже по всей цепочке gateway → auth → accounts.
3. **Ёмкость.** Стенд держит около 1 000 rps с p95 < 5 мс и около 2 000 rps с p95 ~ 22 мс. Насыщение наступает на 2 400–3 000 rps, дальше пропускная способность падает, а p95 растёт до сотен миллисекунд.
4. **Узкое место — общий CPU хоста.** Гипотеза из п.2 подтвердилась.
   - Load average 62 на 8 CPU.
   - Сам nginx тратит меньше, чем любой из основных сервисов.
   - Самый нагруженный сервис — `auth`: по метрикам gRPC он участвует почти в каждом запросе.
   - Я ожидал, что первой закончится память (свободно ~1 ГБ), но этого не произошло.
5. **Предел реального выигрыша.** Все три экземпляра делят одни и те же 8 ядер, поэтому на одном хосте копии не добавляют вычислительной мощности, а только перераспределяют её. Реальный выигрыш появился бы при размещении копий на разных машинах.
6. **Основной экземпляр насыщается первым:** при 2:1:1 на него приходится половина чтений плюс все записи. Если копии перенести на отдельные машины, вес основного экземпляра стоит снижать, например до 1:1:1, оставив ему запас под записи.
7. **Лимит работает и не мешает тестам.** `limit_req` срезает флуд с одного адреса ответами 429 ещё до балансировщика, а доверенная сеть генератора нагрузки позволяет мерить сами бэкенды.
8. **У наблюдаемости есть цена:** на высокой нагрузке p95 вырос примерно вдвое из-за объёма логов. Для продуктивного режима стоит снизить уровень логирования gRPC-вызовов (сейчас пишутся `StartCall`/`FinishCall` на каждый вызов).

## 9. Как повторить

Стенд должен быть запущен (`make web-up`).

```bash
make web-load SCENARIO=steady
make web-load SCENARIO=mixed
RAMP_PEAK=2000 make web-load SCENARIO=ramp
RAMP_PEAK=4000 make web-load SCENARIO=ramp
make web-load SCENARIO=ratelimit
```

**Параметры через переменные окружения:**
- `READ_RPS` (150), `WRITE_RPS` (15), `DURATION` (2m);
- `RAMP_PEAK` (800), `COMPANIES` (5);
- `K6_IMAGE` (`grafana/k6:0.52.0`).

`run.sh` выводит распределение по логу nginx, CPU и окна p95, а файлы сохраняет в `perf/results/web-balance/<сценарий>-<время>/`. Во время прогона это же видно в Grafana: `/monitoring`, дашборд «GoFlow Pay», панели «Чтения основного стека за период» и «Запросы к gateway».
