# GoFlow Pay

---

## Описание проекта

**GoFlow Pay** - это платёжная система для B2B платежей, реализованная на основе микросервисной архитектуры.
Система позволяет компаниям регистрироваться, открывать счета и совершать переводы друг другу через единый API.
Каждый платёж проходит через цепочку проверок: валидацию баланса, обработку транзакции и асинхронное уведомление
участников о результате.
---

## Описание предметной области

Предметная область проекта - сервис для переводов между компаниями и финансовый процессинг. Бизнес регистрируется,
открывает счёт в нужной валюте и может оплачивать услуги партнёров. Каждая транзакция имеет жизненный цикл со статусами
и сопровождается уведомлениями и аудит-записями. Основные сущности предметной области: **Пользователь**, **Компания**, *
*Счёт**, **Транзакция**, **Уведомление**, **Аудит-запись**.

  компонентов.

## Актуальность и целесообразность проекта

Платёжные системы - одна из наиболее востребованных областей в разработке корпоративного ПО. Межкорпоративные расчёты
остаются критически важной частью любого бизнеса, однако готовых открытых решений для изучения внутреннего устройства
таких систем практически нет. GoFlow Pay заполняет этот пробел, предоставляя полноценную учебную реализацию
процессингового шлюза с реальными архитектурными паттернами и подходами.

## Требования к системе

### Функциональные требования (ФТ)
- **1. (Аутентификация и авторизация):** Регистрация пользователя с созданием компании, аутентификация по логину и паролю, выпуск и валидация JWT, разграничение доступа по ролям (Гость, Пользователь, Администратор).
- **2. (Управление счетами):** Открытие мультивалютных счетов компании, просмотр списка счетов, получение актуального баланса, привязка банковских реквизитов.
- **3. (Банковские операции):** Ввод (пополнение) и вывод средств с внутренних счетов через сопряжение с банковскими операциями.
- **4. (Переводы и процессинг):** Инициирование перевода между счетами компаний по идентификатору счета, валидация достаточности средств, атомарный перевод, обеспечение идемпотентности по ключу.
- **5. (Асинхронные уведомления):** Оповещение на почту участников транзакции о смене ее статуса (`pending`, `completed`, `failed`).

### Ключевые нефункциональные требования (НФТ)
- **1. (Производительность / Performance):**
  - Время отклика API чтения баланса и счетов ($p95$) $\le 100$ мс при нагрузке до 500 RPS.
  - Время обработки финансовой транзакции перевода ($p95$) $\le 250$ мс при нагрузке до 150 RPS.
  - Задержка асинхронной доставки событий уведомлений через Kafka $\le 1.0$ с ($p99$).
- **2. (Надежность / Reliability):**
  - Доступность сервиса (Availability) не менее 99.9% в режиме 24/7.
  - Нулевая потеря финансовых транзакций (RPO = 0) благодаря транзакционности в PostgreSQL и паттерну Transactional Outbox (гарантия доставки at-least-once в Apache Kafka).
  - Идемпотентность: повторный запрос на перевод с тем же `idempotency_key` в течение 24 часов не приводит к дублированию списания и возвращает результат ранее созданной транзакции.
- **3. (Безопасность / Security):**
  - Хеширование паролей пользователей с использованием адаптивного алгоритма bcrypt (cost factor $\ge 12$) или Argon2id.
  - Аутентификация на основе stateless JWT (Access Token со сроком жизни не более 15 минут, валидация цифровой подписи на API Gateway).
  - Изоляция сетевого периметра: внешний трафик только по HTTPS/TLS (TLS 1.2+), закрытая внутренняя сеть для gRPC-сервисов и БД, хранение секретов вне репозитория (через environment-переменные).

## Акторы (роли)

**Гость** - неавторизованный пользователь. Может только зарегистрироваться и войти в систему.

**Авторизованный** пользователь - вошедший в систему представитель компании. Может управлять счётом, создавать платежи,
просматривать историю транзакций и баланс.

**Администратор** - авторизованный пользователь с расширенными правами. Дополнительно имеет доступ к аудит-логу всех
транзакций и управлению компаниями в системе.

## Пользовательские сценарии

### Сценарий 1. Регистрация и вход в систему (Гость)

1) Гость открывает приложение GoFlow Pay
2) Гость нажимает кнопку "Зарегистрироваться"
3) Гость вводит email, пароль и название компании
4) Система проверяет что email не занят. Если email уже существует, система показывает ошибку "Пользователь с таким
   email уже зарегистрирован", сценарий завершается
5) Система создаёт пользователя и компанию, возвращает JWT-токен
6) Гость перенаправляется на дашборд как авторизованный пользователь

### Сценарий 2. Создание платежа (Авторизованный пользователь)
1) Пользователь открывает страницу "Платежи" и нажимает "Новый платёж"
2) Пользователь выбирает счёт отправителя, счёт получателя и вводит сумму
3) Пользователь нажимает "Отправить платёж"
4) Система проверяет что сумма больше нуля. Если сумма некорректна, система показывает ошибку валидации, сценарий
   завершается
5) Система проверяет баланс счёта отправителя. Если баланса недостаточно, система возвращает ошибку "Недостаточно
   средств", транзакция переходит в статус "failed", сценарий завершается
6) Система создаёт транзакцию со статусом "pending"
7) Система списывает средства со счёта отправителя и зачисляет получателю
8) Транзакция переходит в статус "completed"
9) Система публикует событие в брокер сообщений, пользователь получает уведомление

### Сценарий 3. Получение выписки по счёту на почту (Авторизованный пользователь)
1) Пользователь открывает страницу платежей.
2) Пользователь нажимает на кнопку "Получить выписку"
3) Открывается форма, для заполнения, в которой пользователь вводит период и счёт, для которого он хочет получить выписку
4) Система отправялет запрос на почту
5) Пользователь открывает почту и получает выписку

## Архитектурные решения (ADR)

### Архитектурный стиль межсервисного взаимодействия: gRPC vs REST / JSON
* **Контекст:** Система GoFlow Pay разделена на независимые микросервисы (`gateway`, `account`, `transaction`, `auth`, `audit`, `notification`). Необходимо определить протокол и формат обмена данными между сервисами во внутреннем контуре.
* **Рассмотренные альтернативы:**
  1. *Внутренний REST по HTTP/1.1 с JSON:* прост в отладке, но влечет значительные накладные расходы на сериализацию/десериализацию JSON, отсутствие строгой типизации контрактов на уровне компиляции и оверхед текстового HTTP.
  2. *gRPC по HTTP/2 с Protocol Buffers:* бинарная сериализация, мультиплексирование потоков в одном TCP-соединении, кодогенерация строго типизированных клиентов/серверов для Go, минимальные задержки.
* **Выбранное решение:** Использовать **gRPC** с Protocol Buffers для всех синхронных межсервисных вызовов внутри защищенного периметра. Внешнее клиентское взаимодействие реализуется через REST API на уровне API Gateway.
* **Причины выбора:** Высокая производительность ($p95 \le 250$ мс), строгие проверяемые контракты `.proto`, экономия сетевых ресурсов при межсервисных запросах.

### Асинхронная доставка событий и консистентность: Transactional Outbox + Kafka vs Синхронный RPC
* **Контекст:** При завершении транзакции перевода требуется уведомить пользователей и зафиксировать событие в сервисе аудита. Прямой синхронный вызов других сервисов в рамках обработки транзакции приводит к сильной связности (coupling), риску распределенных сбоев (dual-write problem) и деградации времени отклика.
* **Рассмотренные альтернативы:**
  1. *Синхронный RPC вызов Audit и Notification сервисов:* блокирует клиентский поток, при сбое сервиса нотификаций транзакция либо откатывается (хотя деньги переведены), либо аудит/нотификация теряются.
  2. *Прямая отправка в Kafka из кода транзакции:* при сбое брокера транзакция в БД сохраняется, но событие не отправляется, что нарушает атомарность (несогласованность БД и брокера).
  3. *Паттерн Transactional Outbox с брокером Apache Kafka:* событие сохраняется в локальную таблицу `outbox` той же ACID-транзакцией БД, что и сама транзакция перевода. Отдельный фоновый воркер надежно доставляет события из `outbox` в Kafka (гарантия at-least-once).
* **Выбранное решение:** Реализовать **Transactional Outbox** в связке с **Apache Kafka**.
* **Причины выбора:** Гарантированное устранение проблемы двойной записи (dual-write), изоляция сбоев (сервис транзакций успешно завершает перевод даже при временной недоступности Kafka или consumer-сервисов), соблюдение требования надежности RPO = 0.
